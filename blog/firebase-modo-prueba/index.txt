30:Te00,<p>Firebase es una de las formas más rápidas de construir una app: autenticación, base de datos y almacenamiento sin montar un servidor. Esa velocidad tiene un costo escondido. En Firebase <strong>no hay un backend que valide cada petición</strong>: la app habla directamente con la base de datos, y lo único que decide quién puede leer o escribir son las <strong>reglas de seguridad</strong>.</p>
<p>Si las reglas están mal, cualquier persona puede leer o modificar los datos de todos tus usuarios, sin necesidad de tu app.</p>
<h2>El modo de prueba</h2>
<p>Al crear una base de datos de Firestore en modo de prueba, Firebase pone una regla parecida a esta:</p>
<pre><code>rules_version = &#39;2&#39;;
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.time &lt; timestamp.date(2026, 12, 26);
    }
  }
}
</code></pre>
<p>Hasta esa fecha, <strong>cualquiera</strong> puede leer y escribir todo. Muchas apps llegan a producción así, y cuando la fecha vence alguien &quot;arregla&quot; el error cambiando la fecha por una más lejana.</p>
<h2>&quot;Solo usuarios autenticados&quot; tampoco basta</h2>
<p>La corrección más común es esta:</p>
<pre><code>allow read, write: if request.auth != null;
</code></pre>
<p>Parece segura, pero en la mayoría de las apps <strong>cualquiera puede crear una cuenta</strong>. Basta registrarse para leer los documentos de todos los demás usuarios. Además, la configuración de Firebase de tu app (incluida la clave de API) está dentro de tu web o tu APK: un atacante no necesita tu app para hablar con tu base de datos.</p>
<h2>Reglas que sí protegen</h2>
<p>La regla debe responder a la pregunta: <strong>¿este usuario es el dueño de este documento?</strong></p>
<pre><code>match /usuarios/{uid} {
  allow read, update: if request.auth != null &amp;&amp; request.auth.uid == uid;
  allow create: if request.auth != null &amp;&amp; request.auth.uid == uid
                &amp;&amp; request.resource.data.keys().hasOnly([&#39;nombre&#39;, &#39;telefono&#39;]);
  allow delete: if false;
}
</code></pre>
<p>Fíjate en tres detalles:</p>
<ol>
<li><strong>Se compara el usuario con el documento</strong>, no solo se verifica que haya sesión.</li>
<li><strong>Se limita qué campos se pueden escribir</strong>, para que nadie se agregue un campo <code>rol: &quot;admin&quot;</code>.</li>
<li><strong>Se niega por defecto</strong> todo lo que no está permitido de forma explícita.</li>
</ol>
<h2>Otras cosas que revisar</h2>
<ul>
<li><strong>Storage</strong> tiene sus propias reglas, separadas de Firestore. Es común proteger la base de datos y dejar abiertas las fotos o los documentos de los usuarios.</li>
<li><strong>Realtime Database</strong>, si la usas, también.</li>
<li><strong>Cloud Functions</strong> que se llaman por HTTP deben verificar quién las llama.</li>
<li><strong>App Check</strong> ayuda a que solo tu app use tu proyecto, pero no reemplaza a las reglas.</li>
<li>El <strong>emulador de Firebase</strong> permite escribir pruebas automáticas de tus reglas. Úsalo.</li>
</ul>
<h2>¿Quieres que las revise?</h2>
<p>La <a href="/servicios/#firebase">Auditoría de Firebase y nube</a> prueba tus reglas con usuarios reales, intentando leer y escribir datos ajenos, y te entrega reglas corregidas listas para copiar. Es lo mismo que se hizo con las reglas de <a href="/control-parental/">Vesta</a>, cuyo backend es <a href="https://github.com/s-Nebula/vesta-api" target="_blank" rel="noopener noreferrer">código abierto</a>.</p>
